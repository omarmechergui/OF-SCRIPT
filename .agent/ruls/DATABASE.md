# 5. MongoDB ObjectId Strategy

MongoDB uses ObjectId identifiers.

Prisma models should use the MongoDB ObjectId mapping.

Conceptually:

```text
id String @id @default(auto()) @map("_id") @db.ObjectId
```

Foreign-key-like relation fields should use compatible ObjectId mappings.

Example:

```text
userId String @db.ObjectId
```

Do not mix identifier formats without a deliberate architectural reason.

---

# 6. ID Rules

Every primary entity must have a unique database ID.

The ID must be:

```text

Stable
Immutable
Never user-controlled
```

Never allow the frontend to choose arbitrary database IDs for normal create operations.



# 11. Username Normalization


Do not allow two users to bypass uniqueness using only capitalization differences.

# 31. Point Transaction Rules

Transactions should be immutable after creation.

Avoid editing historical transactions.

If a correction is required:

```text

        ↓
Correction transaction
```

rather than silently rewriting history.


# 38. Relationship Strategy

Therefore OFFSCRIPT relies on:

```text

+

+

+

```

Services must verify referenced resources before performing operations.

# 39. Orphan Prevention

Before creating a dependent record:

```text

```

```text

```


# 40. Delete Strategy

Avoid destructive deletion when historical relationships matter.

Prefer:

```text
status = ARCHIVED
```

for content such as:

```text
Sessions
Assignments
Projects
Competitions
Badges
```

Historical submissions and points should normally remain available.

---

# 41. User Deletion

User deletion is not a simple database delete.

Before deletion, evaluate:

```text
Submissions
Progress
Points
Badges
Notifications
Files
Audit logs
```

A production implementation should define whether deletion means:

```text
Anonymization
Soft deletion
Account deactivation
Permanent deletion
```

before exposing destructive deletion to users/admins.

---

# 42. Referential Integrity on Updates

Primary IDs should never be changed.

If a parent entity changes:

```text
title
description
status
```

references remain stable.

Never use a mutable title as a relationship key.

---

# 43. Transaction Strategy

Use transactions for operations where multiple records must remain consistent.

Examples:

```text
Session completion + reward
Project approval + reward
Badge unlock + reward
Competition registration under capacity
Point balance + ledger update
```

The transaction boundary must be defined in the corresponding service.

---

# 44. MongoDB Transaction Requirement

Multi-document transactions require a MongoDB deployment configuration that supports transactions.

MongoDB Atlas production deployments support the necessary transaction capabilities.

Development environments must use a compatible MongoDB setup when testing transaction-dependent logic.

---

# 45. Transaction Example

Project approval:

```text
BEGIN
   ↓
Update submission
   ↓
Update progress
   ↓
Create point transaction
   ↓
Create badge if eligible
   ↓
Create notification
   ↓
Audit action
   ↓
COMMIT
```

If a critical operation fails, the transaction should not leave a partially completed business operation.

---

# 46. Idempotency

Database constraints should protect one-time operations.

Examples:

```text
unique(userId, sessionId)
unique(userId, competitionId)
unique(userId, badgeId)
unique(userId, projectId)
```

Points require an explicit idempotency strategy.

---

# 47. Idempotency Key

For reward operations, prefer a deterministic idempotency key.

Example:

```text
SESSION_COMPLETION:userId:sessionId
```

or an equivalent backend-generated key.

The frontend must not be trusted to generate the uniqueness boundary.

---

# 48. Concurrent Requests

The database must protect against race conditions.

Example:

```text
Request A → register
Request B → register
```

Both requests arrive at nearly the same time.

The unique constraint:

```text
unique(userId, competitionId)
```

must prevent duplicate registration.

The service should catch the resulting uniqueness conflict and return an appropriate application response.

---

# 49. Competition Capacity

If a competition has capacity:

```text
capacity = 100
```

registration must not simply:

```text
count registrations
if count < capacity
create registration
```

without considering concurrent requests.

Capacity-sensitive registration requires a deliberate consistency strategy.

---

# 50. Pagination Strategy

Large collections must never be returned without limits.

Examples:

```text
PointTransaction
Notification
Submissions
AuditLog
Users
Competitions
Projects
```

API endpoints should support:

```text
page
limit
```

or cursor-based pagination where appropriate.

---

# 51. Pagination Limits

The backend must enforce maximum page size.

Example:

```text
default = 20
maximum = 100
```

The exact values may be configured.

Never allow:

```text
limit = 100000
```

to create uncontrolled database load.

---

# 52. Sorting

Queries must use explicit sorting.

Examples:

```text
createdAt DESC
```

or:

```text
order ASC
```

For pagination, stable sorting must be used.

---

# 53. Query Projection

Do not retrieve unnecessary fields.

For example, member dashboard queries should not retrieve:

```text
passwordHash
security fields
internal audit metadata
```

Use Prisma `select`/appropriate projections.

---

# 54. Password Data

Never return:

```text
passwordHash
```

through normal API responses.

Password hashes are authentication data and must remain server-side.

---

# 55. Database Security

Do not expose MongoDB publicly without appropriate access restrictions.


Use database/Prisma defaults for appropriate fields.


---

# 61. Nullable Fields

Nullable values must have clear semantics.

Example:

```text
completedAt = null
```

means:

```text
Not completed yet
```

Do not use multiple representations for the same meaning.

Bad:

```text
null
""
0
false
```

for the same conceptual absence.

---

# 62. JSON Fields

JSON should be used only where flexible configuration is genuinely needed.

Appropriate:

```text
Badge.requirementConfig
Competition.eligibilityRules
metadata
```

Avoid storing core searchable relationships inside JSON.

---

# 63. Document Size

MongoDB documents have size limits.

Do not store large uploaded files or unbounded content inside documents.

Large files belong in:

```text
Cloudflare R2
```

Large historical collections must be paginated.

---

# 64. File Storage Boundary

The database stores:

```text
File metadata
```

```text

```

Architecture:

```text

  ↓

  ↓
R2 object
  ↓

```

If metadata creation fails, the service must consider cleanup of the uploaded object to avoid orphaned files.

# 71. Assignment Deadline Integrity

# 72. State Transition Integrity

Database status fields represent current state.

Example:



# 73. Index Design Philosophy

Indexes should answer real queries.

Before adding an index, identify:

```text
What query uses it?
How often?
What collection size is expected?
Does the index improve the query?
What write overhead does it create?
```

Do not create indexes simply because a field exists.

# 75. Database Query Rules

Services should prefer:

```text
Targeted queries
Selective fields
Indexed filters
Pagination
Deterministic sorting
```

Avoid:

```text
Unbounded findMany
Full collection scans
Fetching unused fields
Repeated identical queries
N+1 query patterns
```

---

# 76. N+1 Prevention

When loading related data, inspect the required query shape.

Bad:

```text
Fetch 100 sessions
        ↓
100 separate progress queries
```

Prefer a query/data-loading strategy that retrieves the required related information efficiently.

Do not blindly include every relation.

---

Potential dashboard data:


# 78. Points History Queries


# 79. Notification Queries



# 89. Backward Compatibility

When possible, prefer changes that support old and new application versions during deployment.

Example:

```text
Add optional field
        ↓
Deploy compatible backend
        ↓
Backfill if required
        ↓
Start using field
        ↓
Make required only after verification
```

This reduces deployment risk.

---

# 90. Data Backfill

When existing records need a new field:

```text
Inspect current records
        ↓
Define default/backfill rule
        ↓
Run controlled backfill
        ↓
Verify results
        ↓
Update application assumptions
```

Never assume historical MongoDB documents automatically contain newly added fields.

---

# 91. Backup Strategy

MongoDB Atlas production should have:

```text
Automated backups
Point-in-time recovery where appropriate
Recovery procedure
Access-controlled backup management
```

The team must periodically verify that backups can actually be restored.

A recovery plan should define:

```text
Database outage
Accidental deletion
Corrupted data
Credential compromise
Application/database incompatibility
```

The recovery process must be documented outside the application code as part of deployment operations.

# 94. Data Retention

Retention rules should be defined for:

```text
Audit logs
Notifications
Activity events
Old submissions
Archived content
Files
```

Do not automatically delete historical data without a documented retention requirement.

---

# 95. Database Performance Rules

Prefer:

```text
Indexed filters
Small projections
Pagination
Efficient aggregation
Controlled relation loading
Caching for appropriate read-heavy data
```

Avoid:

```text
Large unbounded queries
Repeated expensive aggregations
Unnecessary document duplication
Massive embedded arrays
```

---

# 96. Embedded vs Referenced Data

Use embedded data when:

```text
Small
Bounded
Read together
Does not require independent lifecycle
```

Use separate collections when:

```text
Large
Frequently queried independently
User-owned
Has its own lifecycle
Requires pagination
Requires independent authorization
```

Examples:

```text
PointTransaction → separate collection
Notification → separate collection
Submission → separate collection
UserBadge → separate collection
```

---

# 97. Array Usage

Avoid unbounded arrays inside User documents.

Bad:

```text
User
 ├── allPoints[]
 ├── allSubmissions[]
 ├── allNotifications[]
 └── allBadges[]
```

Prefer separate collections.

This keeps documents bounded and queries scalable.

---

# 98. Profile Architecture

Profile information remains primarily inside:

```text
User
```

unless a future requirement creates a separate profile domain.

Do not create:

```text
Profile
```

only to duplicate:

```text
username
email
fullName
bio
avatar
```

# 99. Dashboard Architecture

Dashboard is a read model/view over authoritative data.

It should not become a second source of truth.

Dashboard values may be computed from:

```text
SessionProgress
PointTransaction
UserBadge
ProjectProgress
CompetitionRegistration
```

Cached dashboard values must be considered derived.

# 102. Final Database Principles

The OFFSCRIPT database must follow these rules:

```text
MongoDB Atlas is the database.
Prisma is the database access layer.
Mongoose is not used.
ObjectIds are used consistently.
Backend services enforce business rules.
Unique constraints protect critical operations.
Indexes follow real query patterns.
Points are represented by an immutable ledger.
Progress is based on persisted activity.
Badges are idempotent.
Competition registration is idempotent.
Historical data is preserved where required.
Large datasets are paginated.
Files are stored in R2, not MongoDB.
Secrets are never committed.
Database changes are deliberate and tested.
```
